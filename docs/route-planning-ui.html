Design brief · the walk set model

Walk the archive before the light goes

Assemble a handful of markers into a walk, set off from home or wherever you are, get an ordered route through them, know which legs are worth a tram, and see exactly where the daylight runs out. Five ways the interface could work, drawn against the same route so the design is the only thing that changes.

The plan

Five stages, and only two of them cost anything

The route is built cheapest-stage-first. Each stage stands on its own, so the feature can ship in pieces rather than all at once.

A
Order it locally

Nearest-neighbour plus 2-opt over straight-line distance. Instant and offline — and it names the stop the route ends on, which stage B needs before it can run.

free
B
Ask Google once

One computeRoutes call. Origin and destination stay fixed, the markers ride as intermediates, and waypoint optimisation orders only those — which is what makes the result meaningful.

1 request
C
Lay it against the clock

Start time, a flat allowance per stop, arrival and departure for each — then the sunset and twilight lines. Pure local arithmetic.

free
D
Flag the legs worth riding

Only legs over the walking threshold get a transit or taxi lookup, priced at that leg's estimated departure time.

1–4 requests
E
Keep it honest while walking

Position in, stage C re-run with measured pace and dwell. Every tick, for nothing, because the durations are already in hand.

free

The order never changes by itself

Once the walk starts, the sequence is fixed. Times, the cut-off, and the path from where you actually are all keep updating — the order only moves when you ask for it.

Two ways to leave a point out

A scope toggle for the bulk case — all points or only unvisited — and a per-stop skip for the rest. Removed points sit out of bulk fills but can be added by hand, since checking whether something is really gone is a reason to walk there. The route reads this state and never writes it.

The walk starts where you are

Home, a metro exit, or your current position — the origin is a waypoint, not a stop, and it doesn't eat the 25-marker budget. The clock starts when you leave, not at the first pin.

Matrices are the expensive trap

A travel-time matrix is billed per element, so a 15-stop plan runs about $2.25. One optimised route request does the same job for $0.015.

The unit of work

You route a walk set, never a collection

A walk set is a transient, hand-editable list of markers that exists for one walk. It isn't a collection and isn't a filter over the archive — it's a concrete list you build, see, and edit before setting off. Collections become one way to fill it, alongside adding markers by hand.

  • One thing gets routed. "Route this collection" and "route these markers I picked" stop competing — there is a single set, and everything else is a way to fill it. Two collections can feed one walk, which routing a collection directly could never express.
  • The feature stops waiting on collections. Hand-filling needs nothing but the existing marker list, so route planning can ship first. "Add a collection to the walk" is then one extra source, not a prerequisite.
  • The 25-marker cap becomes tractable. A 60-point collection can't be routed, but it can be drawn from. The tray shows 9 / 25, so you trim deliberately instead of hitting a wall.
  • Adding gets simpler than selecting. If markers join from the details overlay that already opens on tap, there's no multi-select gesture fighting the existing map click and no Deck-mode picking to solve. A bulk select mode becomes a convenience, not the only way in.
  • Feasibility gets cheap. A "fits before dark" badge on every collection would mean routing every collection. One set means one estimate, for the thing you're actually assembling.
  • Collections stay untouched. Filling copies marker ids — it doesn't link or subscribe. Editing the walk can never edit a collection.
  • Removed points can still be walked to — just not by accident. Bulk fills skip them, because nobody means to pad a walk with things that are gone. Adding one by hand works, because confirming a removal, reversing a wrong one, or photographing the empty wall are all reasons to go. The itinerary marks it so you remember why it's there.
  • And a good walk can become a collection. The same list of ids travelling back the other way, so it's a create-collection call with a name field once collections exist. Worth being precise in the wording, though: that saves which places, not the route — keeping the sequence is the separate "save this plan" action.

Five directions

Where should the plan live?

Each of these answers that question differently: in a sheet, on a time axis, behind a minimal heads-up display, in a dedicated screen, or inside the collection itself. Same nine points, same October afternoon, same 18:44 twilight — so what you're comparing is the interface and nothing else.

Works when

You want the whole plan legible at once — order, times, modes, and the dusk line in a single scan. It inherits the sheet behaviour the app already ships: peek/full/minimised and the map offset that keeps the active pin clear of the panel.

Falls down

The sheet eats the map. Nine stops plus legs is a long scroll on a phone, and while walking you mostly need one number, not forty. Feasibility is buried at the bottom of the list rather than being the headline.

Notable

The twilight divider sits inside the list, so the stops that don't fit stay visible and dimmed instead of disappearing — the cut is legible as a decision, not a deletion. Swiping a row reveals Пропустить; Обрезать is that same action applied to everything past the divider at once.

Build lowest — reuses an existing pattern

feasibility as the headline

The afternoon drawn as a bar. Stops and legs are blocks along a time axis, twilight is a wall, and everything past it is hatched out. The question "will I make it" is answered before you read a single stop name.

Works when

Deciding whether a plan is worth starting. The shape of the afternoon is visible instantly: where the long legs are, which stop is the tram, how much bar is left past the wall. It makes the trade-off — drop two stops or start earlier — a direct manipulation rather than a calculation.

Falls down

It shows time but not identity. Which two stops are the ones you'd lose? The bar can't say without a list underneath, so this rarely survives alone — it wants to be a header for something else.

Notable

Sunset and civil twilight are separate marks, which makes the half-hour of usable light after sundown a visible resource rather than a hidden assumption.

Build medium — a new component, but pure data you already have

Works when

You're actually out walking with the phone in one hand. Everything not needed in the next six minutes is gone, the map stays legible at arm's length, and the live loop has somewhere quiet to report — the pace correction reads as reassurance rather than noise.

Falls down

Useless for building a route. There's nowhere to see the whole plan, compare stops, or understand which two you're about to lose. It's a mode, not a screen — and shipping it alone would mean shipping half a feature.

Notable

Arriving offers three actions and takes none of them. Walking to a point never marks it visited — the object may be gone, or unreachable, and only the person standing there knows which. Being on the spot is the best moment in the app to log that something has disappeared.

Build low — but only after the sheet exists

Works when

Planning at a desk the night before. Every input that shapes the route is visible and adjustable at once, drag-to-reorder gives the fixed-order rule an honest escape hatch, and the totals update as you fiddle.

Falls down

It's a second home for the map, which the app doesn't otherwise have — new route, new layout, new state to keep in sync with the main map. And nobody plans this way on a phone in the street.

Notable

Manual reorder is the cheapest possible answer to "the cut dropped the wrong stops": no re-solve, no extra request, just drag the one you care about earlier.

Build highest — a new screen and a second map host

Works when

Gathering a walk out of what you already keep. The all/unvisited choice sits exactly where the counts already are, two collections can feed the same walk, and the tray keeps the running total against the 25-marker limit permanently in view.

Falls down

It only answers where markers come from. The set still needs a screen of its own to order, time, and trim — this is a source, not the feature. And a collection bigger than the limit needs the user to choose what to leave out, which a card cannot do for them.

Notable

Filling copies markers rather than linking them, so this never has to answer "what happens to my walk if the collection changes". The fully-visited card is the empty state done right — it reports an accomplishment instead of offering a route.

Recommendation

It isn't a choice of five

Three of these are answering different questions, and the app needs all three answers. Collection card to choose what to walk, itinerary sheet to read the plan, walking HUD as that sheet minimised once you set off. The other two are best harvested rather than shipped.

  • Take the sheet as the surface. The app already runs a bottom sheet on narrow viewports and a 424px side panel on wide ones, with map offsets to match. Route planning gets a proven responsive answer for free, and a second map host never has to exist.
  • Take the light budget as a component, not a screen. Its time bar belongs in the sheet header, where it turns feasibility into the first thing you read while the list underneath supplies the identities the bar can't show.
  • Treat the HUD as the sheet's minimised state. Not a separate design — the same plan, collapsed to the next stop and the day's verdict, which is exactly what the existing minimised/peek/full progression is for.
  • Take drag-to-reorder from the planner, leave the screen. Manual reorder is the honest escape hatch for a fixed-order route, and it works just as well inside the sheet at full height.
  • Put skip on the row, not in a menu. Dropping a stop is the most common edit a walk needs, and it is safe to allow mid-walk — removing a point doesn't reorder the ones left, so the fixed-order rule survives it. The twilight trim is the same action in bulk.
  • Don't plan the way home. Daylight constrains the last photograph, not the walk back — so the route ends at the last marker and the deadline protects the light, nothing else. The API still insists on a destination, so the free local pass names it: the route ends where that ordering ends.
  • Make the walk set the only thing you route. Collections, the map, and search all become sources that pour into one transient set — which means the feature ships without waiting for collections, and two collections can feed a single walk.
  • Give the set a permanent tray. It's what you're building, it needs a running count against the 25-marker limit, and it's the entry point to every other surface here.

Watch the per-card estimates in the collection list — a truthful "fits before dark" badge on every collection implies routing every collection. Start with a straight-line estimate and a hedged label, and only pay for precision on the collection the user actually opens.

Still open

Decide before building

  • Sunset or civil twilight as the deadline? The mocks schedule against twilight at 18:44 and mark sunset at 18:12 — about half an hour of usable light that's worth several stops.
  • What happens past 25 points? One request caps there. Split the collection, cap the route, or route only what's near the start — a 60-point collection needs an answer.
  • Is transit worth building in these cities, or is walk-versus-taxi the only distinction that matters in practice? The leg from home is where to look first — it's usually the longest hop in the route.
  • How much does the derived endpoint cost? The local pass fixes the last stop before Google optimises anything, so its two candidate rules — end of the nearest-neighbour pass, or farthest point from the start — are worth comparing on real clusters.
  • Does the collection list show feasibility for every collection, or only the one you open? The first is better UX and a real cost question.
